## 二、逐条可行性判断

### A. 采纳，照做（事实准、方案对、零依赖、低风险）

1. **流式性能四件套**（memo + useCallback + delta 合帧 + 贴底滚动）——方案专业，特别是报告自己点出「memo 必须连带处理 use-chat-stream 的依赖重建，否则形同虚设」，说明真读了代码。**补充一个更便宜的收口**：`normalizeCitations` 每 delta 对全文跑两遍正则，用 `useMemo(content)` 包住即可，五分钟改完，建议并入四件套。
2. **路由级 React.lazy + Suspense**——815KB 是实测，方案标准。注意 fallback 要复用现有 BootScreen 骨架防闪烁；SlideCanvas/DeckEditor（~2.4k 行）拆出去收益最大。
3. **删除会话确认 / ConfirmDialog 收敛 22 处原生弹窗**——kb 已有 confirm 样板，且 MembersCard 明文密码必须一起修。
4. **联网开关 segmented control、贴底跟随 + 回到底部**——交互判断正确，实现都是局部改动。
5. **搜索竞态 AbortController**——标准修法。
6. **401 后 640ms 人为延迟、BootScreen 骨架、快捷键提示**——小改，随手做。

### B. 采纳，但按核实结果调整

7. **亮色对比度修正——修法有分歧，用我的方案**：报告建议「只改 globals.css 亮色 `--brand`/`--brand-strong`」，**不建议这么做**——全局改 `--brand` 会同时波及主按钮渐变、logo、brand-soft 底等所有用色，牵一发动全身；且 `text-brand` 叠在 `brand-soft` 底上只改 `--brand` 也救不回来。应按走查报告的方案：**逐处把亮色文字换成 `text-brand-deep dark:text-brand`**（约 6 处类名，TaskSidebar 已有现成模式），token 只动 `--text-tertiary`（45%→60% 透明度，一行修全站辅助字）。
8. **窄屏抽屉**：事实半对（丢的是会话列表不是主导航），方案（fixed + translate 抽屉）正确。优先级从 P0 降到 P1——768~1280 的主流窗口下功能没有黑洞。报告标注「风险中：双栏叠加与滚动锁定」是诚实的，做的时候要配滚动锁定（body overflow hidden）。
9. **SSE「继续生成」**：事实修正后方案不变——文本本来就在，只加错误条 + 继续生成按钮（走现成 regenerate 接口），成本比报告描述的更低。
10. **信息架构（experts/skills/mcp 三路由一页）**：事实对，但「合并或拆分」是**产品决策不是工程修复**，需要你拍板；技术上三个真页面只是 HubPage 按路由参数切数据源，成本不大。
11. **品牌色定稿**：不需要「定稿仪式」——favicon 改成青绿就是一行 data URI 的事，青绿已是全站事实标准。建议直接改掉。
12. **react-query 迁移**：方向对但工作量被低估——25 个文件手写 fetch，全迁是周级工程。同意报告自己的排序：先迁高频列表页（kb/agents），WorkspaceSwitcher reload 依赖它，放第三批。**短期妥协**：切工作区 reload 可以先接受现状。
13. **KbPage 拆分（1121 行/29 个 useState）**：属实，纯移动代码零风险，但用户无感知收益，排后。
14. **字阶/圆角 token 收敛**：方向对，「globals.css 收敛 <250 行」低估了（426 行里登录页动效变量占大头），分批做即可。

### C. 缓做 / 不采纳

15. **登录页动效砍到 2 类**：主观判断。登录页是全产品完成度最高的页面，NeuralField 性能也做得好（报告自己也认可），砍动效的收益存疑。缓做，等内页补齐后再回头看。
16. **lucide stroke 统一 1.75**：机械改动、用户无感知，P3。
17. **虚拟化**：报告自己不推荐，我同意——先落 memo 四件套看实测。

## 三、合并两份报告后的修复路线（我的建议）

两份报告互补：设计团队抓到了**工程/性能层**（流式渲染、chunk、数据层——我的走查没覆盖）；我的走查抓到了 **ops 图表大绿块、tertiary token、徽章 1:1、admin 小按钮**（他们的截图走查没发现）。对比度、小字、危险操作两边独立发现，互为佐证。

**第一批（1-2 天，性能+安全）**
- 流式四件套 + normalizeCitations useMemo
- 路由 lazy 分割（815KB→~300KB）
- 删除会话确认 + 登录页 admin123 加 DEV 门禁（走查报告项）

**第二批（3-5 天，可读性+体验）**
- 亮色文字色逐处修正（`text-brand-deep dark:text-brand`）+ tertiary token 一行
- Modal/ConfirmDialog 抽象，替换 22 处原生弹窗（含明文密码）
- 联网 segmented control + 贴底跟随 + 流中切换提示
- favicon 改青绿；ops 趋势图渐隐；徽章底色（走查报告项）

**第三批（1-2 周，结构性）**
- react-query 迁高频页 → 顺带解竞态与 reload
- 窄屏抽屉（会话列表）
- SSE 继续生成；信息架构决策；KbPage 拆分

## 四、一句话结论

**这份报告可以采纳**——18 条事实声明核实了 16 条准确（2 条修正后方案依然成立），工程判断专业（memo 依赖陷阱、虚拟化缓上、零新依赖原则都对），路线图基本可以直接执行。唯一要拦下来的是「全局改 `--brand` 修对比度」这一条：换成逐处 `text-brand-deep dark:text-brand`，其余按它的批次推进即可。
