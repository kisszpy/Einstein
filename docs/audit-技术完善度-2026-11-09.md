# Einstein 技术完善度与生产就绪度评审（v0.6.1 / 2026-11-09）

审阅范围：`server/app`（76 个模块、18.5k 行）、`server/tests`、`.github/workflows/ci.yml`、`web/src`、`deploy/`。只读分析，未改动业务代码。
采信主理人基线，本文只做代码取证与补充；与基线不一致处已标注（见 R8、缺口 F）。

## 1. 一句话结论

**评级：小团队可用（单副本/单机），未达「生产可用」。**
差的不是功能，是三处结构性支撑：①**运行态活在进程内**（`run_registry` 事件日志 + 默认 sqlite 检查点 + 本地暂存目录），第二个副本就开始出错；②**两条安全控制实际未生效**（用户级限流、日请求配额）；③**没有按 run 的因果链**，线上「智能体答错」只能靠翻 stdout。

## 4. 可观测性最小方案（1 页）

**为什么必须先把 `metrics.py` 换掉（核心证据）**：它是 `data/metrics.json` 一个文件 + 进程内 `_cache` + 全局 `threading.Lock`（`metrics.py:13-20`），每次 `record_request` 都 `json.dumps` 整个 dict 再 `write_text` 全量重写（`metrics.py:37-40`、`:52-66`），只留最近 2000 条请求 / 1000 条 LLM 调用。三个后果都是结构性的，不是「以后优化」：①多副本或 backend+worker 共享 `appdata` 卷时**互相覆盖**（锁只在进程内），指标准确性随副本数下降；②**2000 条轮转 ⇒ 跨不过 1 天**，而「月度 token 成本」「上月 p95」这类问题永远答不了；③每请求一次 O(n) 序列化发生在**同步中间件里**（`main.py:199-213`），条目越满、写入越慢，越忙越慢。代码注释自己写了「生产替换点：PostgreSQL 表 / OpenTelemetry」——本方案就是那条替换路径的最小版本。

目标：一次「智能体答错」在 5 分钟内定位到「检索没召回 / 召回错 / 工具选错 / 模型跑偏 / 被中断」。

**表（1 张，迁移 013）**

```sql
CREATE TABLE run_traces (
  run_id TEXT PRIMARY KEY,            -- run_registry.run_id 或 chat 的 conversation+seq
  workspace_id TEXT NOT NULL, owner_id TEXT NOT NULL,
  kind TEXT NOT NULL,                 -- chat | agent | agent_pro | v1_chat | v1_agent | eval
  session_id TEXT DEFAULT '', turn INTEGER DEFAULT 1,
  engine TEXT DEFAULT '', model TEXT DEFAULT '',
  started_at TEXT NOT NULL, finished_at TEXT DEFAULT '', duration_ms INTEGER DEFAULT 0,
  status TEXT DEFAULT 'ok',           -- ok | error | interrupted | approval
  error_kind TEXT DEFAULT '',         -- EmbeddingMismatch | model_timeout | cancelled | ...
  tokens_in INTEGER DEFAULT 0, tokens_out INTEGER DEFAULT 0, llm_calls INTEGER DEFAULT 0,
  retrieval TEXT DEFAULT '{}',        -- {query, rewritten, mode, candidates, hits:[{chunk_id,score}], ms}
  tool_calls TEXT DEFAULT '[]',       -- [{name, ms, status}]
  interrupt TEXT DEFAULT ''           -- approval_required 时记 tool + args_hash
);
CREATE INDEX idx_trace_ws ON run_traces(workspace_id, started_at);
```

**埋点位置（5 处，均为已有函数末尾加一行）**

| 位置 | 记什么 |
|---|---|
| `rag.py:333 search()` 返回前 | mode/candidates 数/两路 top5（`chunk_id, vector_score, lexical_score`）/rerank 是否生效/总耗时 |
| `retrieval.py:52 retrieve()` | 改写前后 query、`error`（EmbeddingMismatch）、`missed` |
| `agent_runtime.py:78 LlmTimer.__exit__` | 已有耗时/token，直接落 `run_traces.tokens_*` + `llm_calls` |
| `routes/agent.py:246 _execute()` 首尾 | run_id/session/status/error_kind/interrupt；`steps` 已有的 tool_call/tool_result 抽成 `tool_calls` |
| `routes/chat.py:201-221` 与 `routes/openapi.py` 各 run 入口 | 同结构写一行（chat 现在完全没有运行记录，只有 messages） |

**查询示例**

```sql
-- 1) 某次答错的完整链路
SELECT started_at, duration_ms, status, error_kind, tokens_in, tokens_out,
       json_extract(retrieval,'$.query') AS q, json_extract(retrieval,'$.hits[0].score') AS top1
FROM run_traces WHERE run_id='…';
-- 2) 今天「检索没命中」占多少
SELECT error_kind, count(*) FROM run_traces
WHERE workspace_id=? AND started_at>=date('now') AND json_extract(retrieval,'$.hits')='[]'
GROUP BY error_kind;
-- 3) 慢在哪：tool vs llm vs retrieval
SELECT kind, avg(duration_ms), avg(tokens_out) FROM run_traces
WHERE started_at>=datetime('now','-1 day') GROUP BY kind;
-- 4) 月度成本（metrics.json 轮转后永远算不出来的那类问题）
SELECT substr(started_at,1,7) AS ym, model,
       sum(tokens_in), sum(tokens_out), count(*) AS runs
FROM run_traces GROUP BY ym, model ORDER BY ym DESC;
```

**能否用现有表承载？** 部分可以：`agent_runs(id, task, steps, answer, status, artifacts, created_at, owner_id)` 已经存了带 `duration_ms` 的 tool_result（`agent_deep.py:571-576`）与 tool_call（`:595-599`），但 ①`short()` 截到 300 字（`agent_runtime.py:17`），命中 chunk_id 与检索 query 都会丢；②没有 token/总耗时/error_kind；③chat 与 `/v1` 完全不写这张表。⇒ 结论：**`agent_runs` 当「回答档案」，`run_traces` 当「排障日志」，不要试图合并**。

**前端测试断层的实际风险（不是「补测试」三个字）**：`web/package.json` 只有 dev/build/typecheck/preview，CI 的 web job 只跑 `typecheck + build`（`ci.yml:73-94`）。这两步能挡的是类型与打包错误，挡不住的是**状态机回归**——而本项目前端恰好有三处高回归面：①`use-chat-stream.ts:80-124` 手写 SSE 事件分发（delta 拼接、`answer_reset` 撤回、error 收尾），任何分支漏改都是「答案少半段」这种不可测出来的问题；②`AgentsPage.tsx:293-430` 的「运行 → 审批 → 续跑」三态（`approval_required` / resume / 超时 404）；③工作区切换（`lib/workspace.ts` + 请求头）跨页面一致性。结论：**不做全量覆盖，按「要改哪里就补哪里」**——①给 `sse-parser.ts` 与一个 `useAgentStream` 加 3-5 个 vitest 用例（纯函数，无 DOM，成本 <1 天）；②加 1 条 Playwright E2E 冒烟（登录 → 提问 → 看到 delta → 完成），只在 release 分支跑。理由：R16（KB 文档管理接入）与 R14（SSE 统一层）都要动这几处，先有护栏再动刀，比事后补便宜。

**另外 27 个 verify_*.py 的取舍**（CI 现跑 3 个）：留 6 个进 CI —— `verify_contracts`(已)、`verify_queue`、`verify_state_backends --only sqlite`(已)、`verify_isolation`、`verify_rbac_http`、`verify_hitl_e2e`；其余（`verify_m6`/`verify_s25`/`verify_s26`/`verify_p0_fixes` 这类「某次迭代验收」）标记 `@pytest.mark.slow` 只在 release 分支跑，或直接归档到 `docs/` 下当历史证据——它们的内容多数已被 pytest 覆盖，留着只增加 `test_verify_scripts` 的维护成本。
