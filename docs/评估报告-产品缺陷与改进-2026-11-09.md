- 评估日期：2026-11-09

## 一、结论摘要

产品的主体能力是扎实的：混合检索、切片策略、去重与版本、项目级文件边界、用户级隔离都有实现，且配了 28 个验证脚本（4554 行）兜底。问题集中在**"用框架的壳、但没吃到框架的语义"**：LangGraph 的持久化与中断语义没接，于是人工确认变成"重跑整个任务"；检索链路的参数在两条入口不一致，于是同一知识库在对话里准、在智能体里碎。

按影响面排序，需要先处理的六件事：

| # | 级别 | 缺陷 | 一句话影响 |
|---|---|---|---|
| 1 | P0 | 审批 = 重跑：无 checkpointer，`ApprovalRequired` 靠抛异常中断 | 批准后整个任务从头再来，已执行的写操作会重复 |
| 2 | P0 | 相关性阈值形同虚设（`MIN_SIMILARITY=0.01`） | 不相干的问题也会返回 3 条片段，"知识库未命中"分支几乎不可达 |
| 3 | P0 | 审批状态存进程内存、无归属校验、永不过期 | 重启即失效；同会话批一次永久放行；`/approve` 可用别人的 session_id |
| 4 | P0 | 默认 deep 引擎暴露 `execute` 但后端不支持 | 模型白调一次工具、拿到英文错误，打断计划 |
| 5 | P1 | 智能体回答是"假流式"（生成完再切片下发） | 首字延迟 = 全文生成时间，本地 27B 下体感最差的就是这里 |
| 6 | P1 | 两条路径的检索参数不一致（父片展开/改写/引用/重排） | 同一知识库，对话模式准、智能体模式碎，且答案无法溯源 |

## 三、先说做对了什么（这些不要动）

评估不能只挑毛病，以下五处是被反复验证过的正确决策，后续改造要保住：

1. **项目边界落在 backend 层**：`FilesystemPermission` 是构建期快照且与 execute-capable 后端互斥（框架 `middleware/filesystem.py:2087-2096` 直接 `NotImplementedError`），而 `project_create` 会在运行中改写活动项目——把边界做进 `WorkspaceBackend` 是唯一正确的位置，且顺带解决了"技能目录只读"。
2. **技能渐进披露 + 每任务热同步**：`.agent/skills/` + `pinned_skills` 让"点名的技能一定装载、没点名的按需发现"，比把技能塞进系统提示词高一个量级。
3. **检索融合的骨架是对的**：dense + BM25 双路 + RRF + 可选重排 + 父片展开 + 文档去重与版本快照，缺的是参数校准与门面统一，不是重写。
4. **隔离与配额有真实的执行点**：`owner_id` 贯穿七表、越权统一 404、请求级配额在中间件里真的会拦（`main.py:100-106`）、登录/接口限流按维度分开。
5. **28 个 verify 脚本**：虽然没进 CI，但断言写得很具体（库边界、隔离、续跑、契约），迁移到 pytest 的成本很低——这是最划算的一笔技术改造。

## 四、RAG 链路缺陷（技能：langchain-rag）

### 4.1 【P0】相关性阈值形同虚设，"未命中"分支不可达 — ✅ 已修复（0.5.1）

证据：
- `rag.py:41` — `MIN_SIMILARITY = 0.01`，注释自己写明"嵌入模型对完全不相关文本也会给出 0.2~0.5"；
- `rag.py:327` — 向量路只做 `s > 0.01` 的过滤，等于不过滤；
- `rag.py:337-347` — hybrid 用 RRF 只看排名，低相似度命中照样拿到融合分；
- `tools.py:83-87` — `kb_search` 只在 `hits` 为空时返回"没有找到"，而阈值 0.01 下几乎不可能为空。

影响：任何问题（包括知识库完全不覆盖的问题）都会拿到 3 条最相似的片段；而系统提示词第 3 条要求"答案必须以知识库为准"（`tools.py:110-111`）。这不是检索缺陷，而是**幻觉的生成装置**：噪音被当成证据，还被要求优先采信。

修法：
1. 阈值改成绝对语义：`rerank` 有分就用重排分设门限（如 0.2），没有就用余弦设门限（如 0.35），并按语言/模型标定一次；
2. `kb_search` 返回里带 `score` 与来源编号，让模型能判断"这条不太相关"；
3. 阈值不达标时返回显式的"知识库未命中"，并把该分支写进评测集（负例）。

### 4.2 【P0】重排默认关闭，但代码按"已重排"的语义在写

证据：`config.py` 检索段 `rerank_provider: str = "none"`；`rag.py:371-374` 无条件调用 `rerank_hits(..., top_k)`；`rerank.py:169` 在 `provider == "none"` 时直接原序返回。

影响：文档与代码注释都在讲"三级降级重排"，实际默认不生效，排序质量完全取决于 RRF；同时 `kb_search` 拿不到任何绝对相关度，4.1 的门限也就无从做起。

修法：二选一，但别含糊——要么把 `http`/`onnx` 之一设为默认（本地有 bge-reranker 就跑 onnx），要么在检索响应里显式带 `rerank: "none"`，并在评测集里跑一组开/关对比，把差异写进文档。技能里明确 reorder = 可配置的独立环节，不该是"看起来有"。

### 4.3 【P1】嵌入调用不分批，且不记模型身份 — 🟡 分批已修复（0.5.1），模型指纹待做 — ✅ 已补指纹（0.6.0）

证据：
- `embeddings.py:85` — `_remote_embed(list(texts))`，一篇文档的所有切片一次性发一个请求，超时 60s、重试 1 次；
- `rag.py:161` — chunk 只记 `embedding_kind`（`remote`/`mock`），不记模型名与维度；
- `vector/milvus.py:105-107` — 写入时维度冲突会报错（这点做得对）；
- `vector/memory.py:41` — 降级到内存计算时**静默丢弃**维度不符的切片，返回空列表。

影响：一本 300 页 PDF（约 1500 片 × 500 字 ≈ 75 万字）压进单请求，60s 必然超时，用户看到的是"嵌入端点不可用"；换嵌入模型（8B→4B，维度 4096→2560）后，写入报"维度冲突"但错误文案不指向根因，检索侧若走内存降级则静默返回空——hybrid 只剩 BM25，没人会发现。

修法：
1. 按批切（如 64 条或 8 万字符/请求），逐批重试，失败批次可续；
2. chunk 记 `embedding_model` + `dim`，检索前做一次指纹校验，不匹配直接给出可操作错误（"请重建索引：tools/rebuild_vector_index.py"）；
3. memory 后端遇到维度不符不要静默过滤，计数并打日志。

### 4.4 【P1】parent-child 切片只在对话路径生效 — ✅ 已修复（0.5.1）

证据：
- `chat.py:204-205` — `search(..., top_k=4, parent_expand=True)`；
- `tools.py:84` — `kb_search` 用默认参数（`parent_expand=False`）；
- `tools.py:128` — `preflight_kb` 同样不展开。

影响：一旦给文档选了 parent-child 策略，智能体拿到的是 250 字的孩子片，同父兄弟不拼回，回答天然碎片化；同一知识库在对话里完整、在智能体里残缺，用户会归因为"智能体不聪明"。

修法：把检索参数收敛成一个 `retrieve(kb_ids, query, *, for_answer: bool)` 门面，对话与工具共用；技能里的 parent-child 语义本来就是"孩子片检索、父片作答"，缺一半等于没做。

### 4.5 【P1】智能体答案无引用，无法溯源 — ✅ 已修复（0.5.1）

证据：`api/routes/chat.py` 有 `citations` 事件（5 处），`api/routes/agent.py` 全文件 0 处。

影响：对话模式能点开看原文切片，智能体模式只有一句"依据知识库"，出了错无法举证，也无法做"答案→切片"的评测。

修法：`kb_search` 的返回值带 `[n] 文档名#chunk_id`；引擎在 final 帧附带本次检索到的 citations（`AgentContext` 里攒，和 artifacts 同一机制）。

### 4.6 【P2】无 MMR/多文档配额，top_k 固定 3 — 🟡 文档配额已修复（0.5.1），MMR 待做

证据：`tools.py:84` `top_k=3`；`rag.py` 全文无 mmr 或"每文档最多 N 片"约束。

影响：一篇结构重复的文档（制度、合同模板）容易占满 3 个名额，跨文档对比类问题必然缺证据。

修法：先加"每文档最多 2 片"的硬约束（比 MMR 便宜且可预测）；有预算再上 MMR。

### 4.7 【P2】BM25 每查询全量重建

证据：`rag.py:331-332` — 每次 `search` 都对目标库全量切片 `BM25([...])`；`rag.py:312` 全量 `list_chunks`。

影响：知识库上万片后，每次检索多几百毫秒 CPU，且与查询长度无关的固定开销。

修法：按 `kb_id` 缓存索引，用 `documents.updated_at`/切片数做失效键；缓存键里带库版本，删除/重建时主动清。

## 五、Deep Agents 运行时（技能：deep-agents-core）

先说明核查结果：框架默认装配的东西我们其实拿到了——运行时探测确认工具集为
`ls / read_file / write_file / edit_file / glob / grep / delete / execute / write_todos / task`，
其中 `task` 来自框架自动追加的 `general-purpose` 子智能体，`SummarizationMiddleware` 也是默认安装（`graph.py:934-940`）。所以**"没有子智能体、没有上下文压缩"这两条不成立**，不要照抄网上的旧结论。真正缺的是持久化与记忆。

### 5.1 【P0】没有 checkpointer / thread_id，运行状态不可恢复 — ✅ 已修复（0.5.1）

证据：
- `agent_deep.py:_build_agent` 调 `create_deep_agent(...)` 时未传 `checkpointer`；
- `_iter_events` 的 `astream(..., config={"recursion_limit": ...})` 未带 `thread_id`；
- `api/routes/agent.py` 自行用 `session_id` 存业务历史，与图状态无关。

影响（逐条对应框架语义）：

| 框架能力 | 现状 | 后果 |
|---|---|---|
| 中断后 `Command(resume=...)` 续跑 | 用不上 | 审批只能重跑（见 6.1） |
| 多轮共享同一线程状态 | 没有 | todos 只活在一次请求里 |
| 断点回放 / 时间旅行 | 没有 | 出错只能复现，不能定位 |
| 客户端断连后恢复 | 没有 | 任务直接消失（见 6.3） |

修法（技能标准姿势）：`checkpointer=AsyncPostgresSaver(...)` + 每次运行 `config={"configurable": {"thread_id": session_id}}`。

> **0.6.1 已落地**：`app/services/checkpoints.py` 按 `APP_AGENT_CHECKPOINT` 分档（auto / sqlite / postgres / memory / off），
> 默认 `auto` 跟主存储走。强杀进程再重启，批准后仍从断点续跑（`tools/verify_checkpoint_restart.py` 实测）。
> 遗留：Windows 上 psycopg 不能跑在 Proactor 循环，postgres 档只在 Linux 可用。

### 5.2 【P0】默认 deep 引擎暴露 `execute`，但后端根本没有执行能力 — ✅ 已修复（0.5.1）

证据（运行时探测，非推断）：
- `_build_agent(...)` 产出的 tools 节点里包含 `execute`；
- `WorkspaceBackend` 的 MRO 为 `WorkspaceBackend → FilesystemBackend → BackendProtocol`，**没有 `execute`**；
- 框架 `middleware/filesystem.py:3237-3243`：不支持执行时返回
  `"Error: Execution not available. This agent's backend does not support command execution..."`。

影响：模型看到"能跑命令"的工具，很可能先试一次，拿回一段英文报错，再改道 `code_run`——一次白跑的工具调用 + 计划被打断。`.env` 当前是 `deepagents-pro`，所以这条是**默认引擎的潜在雷**，一旦回滚到 `deepagents` 就炸。

修法：两条路选一条——① 默认引擎装配时把 `execute` 从工具集中排除（Pro 才有）；② 默认引擎直接换成"不支持执行"的提示词 + `code_run` 单一入口，并在装配层断言"工具集 ⊆ 后端能力集"。别靠提示词告知模型"别用 execute"。

### 5.3 【P1】长期记忆（Store / MemoryMiddleware）没接，智能体不带任何背景 — ✅ 已接入（0.6.0）

证据：`chat.py:189-195` 有 `memory_service.relevant_memory` 注入；`agent_deep.py` 全文无 memory 相关装配，`create_deep_agent` 未传 `store=`。

影响：用户在对话里说过的偏好、约束，切到智能体执行时全部丢失；两套引擎两套记忆，产品上表现为"它怎么又忘了"。

修法：短期把 `memory_service` 的命中结果注入系统提示段（与 chat 同一份实现）；中期上 `store=` + `MemoryMiddleware`，让记忆成为框架状态而不是每轮拼字符串。

### 5.4 【P2】`task` 子智能体可用，但提示词完全没提

证据：`DEEP_SYSTEM_PROMPT`（`agent_deep.py`）通篇是"你自己怎么干"，没有任何"何时委派给子智能体"的引导；而工具集里确实有 `task`。

影响：本可以隔离上下文的资料收集、长链路检索，全压在主上下文里，靠 64 步预算 + 3 次续跑硬扛——这也是之前"任务超时/撞上限"的根因之一。

修法：在计划段加一条委派规则（技能里的 `when-to-use-subagents`）：资料收集、批量页面核对、独立子报告 → `task(agent="general-purpose", instruction=... )`，并要求一次给全指令（子智能体无状态），返回摘要而非全文。

### 5.5 自研保留项：预算续跑

`agent_deep.py:53-54` 的 `RECURSION_LIMIT=64` + `MAX_BUDGETS=3` + 续跑注入是**合理的自研**：框架的 `recursion_limit` 只有报错语义，没有"触顶续接"。保留，但注意两点：

1. 续跑把全量历史消息重新入图，token 成本随轮次线性上升；
2. 续跑期间 todos 靠 `carry` 手工搬运——一旦上 checkpointer，这部分可以交回框架，代码应同步删减。

## 六、编排与人工确认（技能：deep-agents-orchestration）

### 6.1 【P0】审批不是 `interrupt`：批准 = 重跑整个任务 — ✅ 已修复（0.5.1）

证据链（完整走通）：
1. `capabilities/__init__.py:288-289` — 未批准的 `code_run` 直接 `raise ApprovalRequired(...)`；
2. `agent_deep.py:527-536` — 捕获后吐 `approval_required` 事件并结束本轮（图被异常中断）；
3. `web/src/features/agents/AgentsPage.tsx:397` — 批准后 `run(submitted)` **重发原始任务**；
4. 服务端 `_APPROVALS` 只记了"这个 session 允许这个工具"，没有任何已完成步骤的恢复信息。

影响：批准后的第二次运行从第一步重来。已写过的文件再写一遍、MCP 工具再调一次、已花掉的 token 再花一次；步骤流归零，用户看到的是"任务重跑"而不是"继续"。技能里写得很清楚：HITL 的语义是 **interrupt 发生在两次 invoke 之间**，用同一 `thread_id` + `Command(resume={"decisions":[{"type":"approve"}]})` 续跑，这才是"继续"。

修法：
```python
agent = create_deep_agent(
    ...,
    interrupt_on={"code_run": True},
    checkpointer=checkpointer,          # 必须
)
# 首次运行
await agent.ainvoke(inputs, config={"configurable": {"thread_id": session_id}})
# 恢复
await agent.ainvoke(Command(resume={"decisions": [{"type": "approve"}]}), config=same)
```
顺带拿到两个现在没有的能力：
- `{"type": "reject", "message": "先跑测试再执行"}` → 模型换路线，而不是干等；
- `{"type": "edit", "edited_action": {...}}` → 批准前改参数（比如把 `rm -rf` 改成限定目录）。

### 6.2 【P0】审批状态：进程内存 + 无归属校验 + 永不过期 — ✅ 已修复（0.5.1）

证据：`api/routes/agent.py:82-95`
- `_APPROVALS: set[tuple[str, str]]` 是模块级内存，多 worker 不共享、重启即清；
- `/approve` 只校验"登录 + 工作区"，不校验 `session_id` 是否属于当前用户；
- 批准粒度为 `(session_id, tool)`，一旦批准，该 session 后续所有该工具调用永久放行。

影响：单机重启后用户再点一次（注释里认为可接受）尚可，但"用别人的 session_id 预批准"是实打实的越权面；"批一次永久放行"与"逐次确认"的产品预期不符。

修法：审批状态跟 thread 绑、落库（Postgres 已有）、带 TTL（如 30 分钟或本次运行）；`/approve` 校验 session 归属；粒度改为 `(thread_id, tool, 参数指纹)`，参数变了重新确认。

### 6.3 【P1】客户端断连即取消，失败运行不入库 — ✅ 已修复（0.6.0）

证据：`api/routes/agent.py:239-244` — `finally: pump.cancel()`；`history.add_agent_run(...)` 只在成功路径（`259-273`），异常路径只吐 `error` 事件。

影响：刷新页面、切网、点了"停止"，任务被静默取消；产物可能已经落在磁盘上，但历史里没有这次运行，用户以为"没跑过"。这跟"智能体是异步长任务"的产品定位直接冲突。

修法：运行与视图解耦——后台任务跑图（配 checkpointer），SSE 只做订阅；断连不取消，重连从 `thread_id` 拉状态；失败也写一条 `status=failed` 的历史。

### 6.4 【P2】TodoList 只活在单次请求内

证据：`_iter_events` 把 `todos` 放进 `carry` 手工传递；没有 checkpointer，跨请求无法恢复。

影响：暂停→批准→重跑后，计划重新拆一遍，且可能与上次不一样；用户看到的计划列表跳变。

修法：随 5.1 一并解决——todos 是图状态的一部分，`state.todos` 持久化后天然恢复。

## 七、产品一致性与体验

### 7.1 【P1】智能体回答是"假流式" — ✅ 已修复（0.6.0）

证据：`agent.py:35` `streaming=False`（注释自认"最终回答再切片下发"）；`api/routes/agent.py:246-248` 拿到 `final_text` 后用 `chunk_text(24)` 切片吐 `delta`。

影响：首字延迟 = 全量生成时间。本地 27B 生成长回答时，用户盯着"正在执行"几十秒，然后文字"唰"一下全出来——和对话模式的逐字流是两种体验。

修法：改用 `astream_events`，订阅 `on_chat_model_stream` 直接下发增量；工具事件与 token 事件双通道，路由层只做转发。技能侧没有限制这种做法，deepagents 的 `astream` 本来就支持 `messages` 流模式。

### 7.2 【P1】同一知识库，两条入口两套检索行为 — ✅ 已修复（0.5.1）

汇总（同一份 `search()`，参数完全不同）：

| 行为 | 对话（chat.py） | 智能体（tools.py） |
|---|---|---|
| 查询改写 | 有（`rewrite_query`，追问消解） | 无 |
| 父片展开 | 有（`parent_expand=True`） | 无 |
| top_k | 4 | 3 |
| 引用回传 | 有 `citations` | 无 |
| 长期记忆 | 有 | 无 |

影响：同一份资料，问一句话得到一个答案，让智能体做同一件事得到另一个答案，且后者更差。这类不一致最难排查——两个入口都"能用"。

修法：抽 `retrieve()` 与 `compose_system()` 两个门面，所有入口共用；引擎只负责"怎么想"，不负责"怎么查"。

### 7.3 【P2】项目 slug 空值回落 `untitled`，会撞名 — ✅ 已修复（0.5.1）

证据：`capabilities/sandbox.py:32-35` — `slugify` 在清洗后为空时返回 `"untitled"`。

影响：项目名叫 `🚀`、`+++`、纯 emoji 时都会落到 `untitled`；第二个同类项目直接复用第一个的目录（`projects.require` 已存在即视为同一个），用户会觉得"我的项目串了"。此前盘上出现的 `data/projects/default/untitled/` 就是这条路径的产物。

修法：slug 为空直接拒绝并提示"项目名需包含中英文或数字"；存量 `untitled` 目录做一次提示性迁移。

### 7.4 【P2】浏览器每次调用新起 Chromium — ✅ 已修复（0.6.0）

证据：`capabilities/browser_pro.py:190` — 每次 `open_page` 都 `p.chromium.launch(args=["--no-sandbox"])`，用完 `close`。

影响：每次 1-2 秒的进程启动开销（还未计浏览器冷启动与首包），连续抓三个页面就多花 5 秒；`--no-sandbox` 在宿主上跑等于关掉浏览器沙箱。

修法：进程内单例 `browser`，每次任务新建 `context`（cookie 隔离）；`--no-sandbox` 只在容器里加（容器本身已是隔离边界）。
