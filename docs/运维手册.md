# 运维手册

面向部署与值守，不解释业务设计。设计取舍见 [开发进度-第二阶段.md](开发进度-第二阶段.md)。

## 1. 拓扑与端口

| 组件 | 容器内端口 | 宿主机（prod） | 说明 |
|---|---|---|---|
| web (nginx) | 80 | `WEB_PORT`（默认 80） | 唯一对外入口 |
| backend | 8000 | `BACKEND_PORT`（默认 8000） | 调试可直接访问 |
| worker | — | — | 无端口，消费队列 |
| postgres | 5432 | 不暴露 | 业务数据 |
| redis | 6379 | 不暴露 | 任务队列 |
| milvus | 19530 / 9091 | 不暴露 | 向量库 + 健康检查 |
| etcd / minio | 2379 / 9000 | 不暴露 | Milvus 依赖 |

开发用 `deploy/docker-compose.yml` 才把 5433 / 6380 / 19530 映射到宿主机，便于本机调试。

## 2. 首次部署

```bash
cp deploy/.env.example deploy/.env      # 必填：数据库密码、LLM/嵌入端点
docker compose -f deploy/docker-compose.prod.yml up -d --build
docker compose -f deploy/docker-compose.prod.yml ps       # 等 health 全绿
```

首次启动会自动建表（迁移 001–005）并创建管理员 `admin / admin123`。
**上线第一件事：登录后到「系统管理 · 成员」改密码。**

模型端点如果在宿主机上（llama.cpp / vLLM），`APP_LLM_BASE_URL` 用
`http://host.docker.internal:8080/v1`；Linux 下需要 compose 里加
`extra_hosts: ["host.docker.internal:host-gateway"]`。

自检：

```bash
docker compose -f deploy/docker-compose.prod.yml exec backend python tools/check_infra.py --deep
```

五项全绿（pg / redis / milvus / llm / embedding）才算部署完成。

## 3. 日常巡检

```bash
# 服务与健康
docker compose -f deploy/docker-compose.prod.yml ps

# 后端日志（最近 200 行）
docker compose -f deploy/docker-compose.prod.yml logs --tail 200 backend
docker compose -f deploy/docker-compose.prod.yml logs --tail 200 worker

# 队列积压：pending 应该接近 0
docker compose -f deploy/docker-compose.prod.yml exec backend \
  python -c "from app.services.queue import get_queue; print(get_queue().stats())"

# 检索链路（不带 LLM，只看嵌入与召回）
curl -s -X POST localhost:8000/api/kb/search \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $TOKEN" \
  -d '{"kb_ids":["<kb>"],"query":"死锁","top_k":3}'
```

关注三件事：`pending` 是否持续增长、`failed` 是否出现新任务、audit 里 5xx 占比是否上升。

### 3.1 变更后冒烟

改配置、换镜像、升级依赖之后，别只看 `/api/health` 返回 200 —— 那只证明进程活着。
跑一遍编排冒烟，它按真实用户路径走：登录 → 建库 → 摄入 → 检索 → 流式对话。

```bash
bash deploy/smoke_compose.sh --no-build      # 起容器整套验
bash deploy/smoke_compose.sh --infra-only    # 只验编排与鉴权，不依赖模型端点
SMOKE_BASE=http://10.0.0.5:8000 bash deploy/smoke_compose.sh --no-compose   # 打已有实例
```

失败项会直接给出方向：容器 `unhealthy`、任务卡 `pending`（worker 没跑）、SSE 收不到 `done`（反代缓冲）。

### 3.2 花在哪、谁在用（成本与告警）

控制台「运营」页和下面几个接口看同一批数据，都是 `run_traces` 的聚合：

```bash
# 近 7 天：总额 + 按天 / 按模型 / 按成员 / 按入口（by_kind 目前只有 chat 与 agent）
curl -s "localhost:8000/api/obs/cost?days=7" -H "Authorization: Bearer $TOKEN"

# 模型端点清单与最近一次探活结果（has_key / key_hint，永远不回明文密钥）
curl -s localhost:8000/api/models -H "Authorization: Bearer $TOKEN"

# 手动跑一次告警评估；/alerts/events 看投递结果
curl -s -X POST localhost:8000/api/alerts/check  -H "Authorization: Bearer $TOKEN"
curl -s "localhost:8000/api/alerts/events?limit=50" -H "Authorization: Bearer $TOKEN"
```

三个判据：

- **`by_model[].priced=false`** —— 这个模型没填单价，成本算成 0。不是"免费"，是"没记账"，
  去「模型」页补 `price_in/price_out`；补完只影响之后的花费，历史账不动（快照在 `finish()` 时定格）。
- **`cost` 蹭涨但 `by_member` 集中在少数 id** —— 先看这些 id 的智能体会话：长任务 + 大上下文
  是常见原因，其次是反复重试（`errors` 同步升高）。
- **`/alerts/events` 里 `delivered=false`** —— 规则命中了但 webhook 没送出去（域名拼错、
  机器人被移出群、出口被拦）。告警没送出去比没配告警更危险，页面上会标红。

口径说明：这张账只算走过对话与智能体的调用（`run_traces` 的 `kind` 是 `chat` / `agent`）。
评测、嵌入、重抓这类后台消耗在 `metrics` 里按次数计，不进成本看板——它们的单价和调用量
都不由用户直接触发，混进同一张账会让"谁在花钱"说不清。

后台每 `APP_ALERT_INTERVAL_MINUTES` 分钟评估一次（`main.py` 的 `alert_loop`），
与手动 `/alerts/check` 共用同一份逻辑，冷却时间按规则分别计。

## 4. 备份与恢复

```bash
cd server
python tools/backup.py backup                                   # 按当前后端
python tools/backup.py backup --backend postgres --pg-container einstein-postgres
python tools/backup.py list
python tools/backup.py restore backups/einstein-xxx.tar.gz --yes
```

- 备份包含：业务数据（pg dump / sqlite 快照 / json 状态文件）+ `data/uploads` 未处理的上传文件
- 备份含 API Key 与用户口令摘要，按密钥物料保管，不要放公共存储
- 建议节奏：每日全量 + 重大变更前手动一次；恢复后必须重启 backend 与 worker

SQLite 后端用 `sqlite3` 在线备份 API，不会锁库；JSON 后端直接复制状态文件，写入是原子替换，
所以并发备份也不会拿到半截文件。

### 4.1 保留策略与自动清理

备份不能只加不减：一次全量在实测环境里 100~130 MB，每日一份、留一年就是 40 GB。
两条规则同时生效（`--keep` 管份数，`--days` 管年龄）：

```bash
python tools/backup.py backup --prune 14          # 备份完只留最近 14 份
python tools/backup.py prune --keep 14 --days 30  # 单独清理：留 14 份、且不超 30 天
python tools/backup.py list                       # 带大小与"几天前"，一眼看出有没有断档
```

只按份数保留有个坑：连续一周备份失败时，最后 14 份可能全是上个月的老包，
看着"还有 14 份"其实最新的已经过期。所以生产建议 **份数 + 天数都设**。

### 4.2 恢复演练（verify）

```bash
python tools/backup.py verify --file backups/einstein-20261109-234723-postgres.tar.gz
python tools/backup.py verify --file backups/          # 目录下全部检查
```

逐项核对：归档可读、manifest 存在、列出的文件都在、没有 0 字节文件；
sqlite 额外跑 `PRAGMA integrity_check` 并确认有表，json 逐份解析，
pg_dump 检查文件头与 `COPY` / `CREATE TABLE`。**任一项失败以非 0 退出**，
可以直接挂进 cron 或 CI。

它挡的是最阴的一类事故：备份脚本"每天成功"，产出的却是空包，等真恢复时
才发现——那时损失的是整个保留周期。建议把 verify 放在备份之后立刻跑，
失败即告警（告警通道见 3.2）。

### 4.3 定时任务

cron（Linux）示例，每天 02:30 备份 + 校验 + 保留 14 份：

```cron
30 2 * * * cd /opt/einstein/server && \
  .venv/bin/python tools/backup.py backup --prune 14 >> logs/backup.log 2>&1 && \
  .venv/bin/python tools/backup.py verify --file "$(ls -t backups/*.tar.gz | head -1)" >> logs/backup.log 2>&1 \
  || echo "备份或校验失败" >> logs/backup.log
```

Windows 用任务计划程序，操作填：

```
程序：C:\path\to\server\.venv\Scripts\python.exe
参数：tools\backup.py backup --prune 14
起始于：C:\path\to\server
```

**恢复演练**不必每天跑，但每季度要做一次真的：把最近一份备份 restore 到
一台隔离机器，登录、检索、打开一段对话，确认数据真的是"那天的"。只跑
verify 只能证明包没坏，证明不了"恢复流程还能走通"。

## 5. 升级

```bash
git pull
docker compose -f deploy/docker-compose.prod.yml build backend worker web
docker compose -f deploy/docker-compose.prod.yml up -d
docker compose -f deploy/docker-compose.prod.yml exec backend python -c \
  "from app.db.engine import get_db; from app.db.schema import migrate; print(migrate(get_db()))"
```

迁移只增不改，可重复执行，返回本次应用的版本号（空列表表示已是最新）。
**先备份再升级**，回滚靠备份恢复 + 回退镜像 tag。

升级完先跑 `bash deploy/smoke_compose.sh --no-build` 再放流量。CI 里的 `tools/verify_contracts.py`
会拦住"只在某个后端漏实现方法"这类问题，但运行期行为（队列、SSE、反代）只有冒烟能确认。

### 5.1 跨后端迁移（json / sqlite / postgres）

从"零依赖起步"换成生产组合，是这套系统最常见的一次性动作。顺序错了会出现
"接口写 PG、后台任务读 SQLite"这种半套状态——两边都能跑，数据却对不上。

```bash
# 1. 停写：先把 backend 与 worker 停掉（否则迁移过程中新数据会落在旧库）
docker compose -f deploy/docker-compose.prod.yml stop backend worker

# 2. 起目标依赖（pg 5433 / redis 6380 / milvus 19530）
cd deploy && docker compose up -d && cd ../server
python tools/check_infra.py --deep

# 3. 迁移数据（幂等，可重复跑；只迁"配置域 + 知识库 + 会话"）
python tools/migrate_json_to_db.py --backend postgres

# 4. 打开开关后重启：APP_STORE_BACKEND / APP_VECTOR_BACKEND / APP_QUEUE_BACKEND
#    向量必须重建——json 后端下向量在内存里，换后端等于没有
python tools/rebuild_vector_index.py --reembed --drop

# 5. 校验：规模对得上再放流量
python tools/report_capacity.py
```

四件事容易做错：

- **只改配置不迁数据**：新库是空的，界面看着正常、内容全没了；
- **忘了重建向量**：配置域迁过去了，检索却一条不命中（`report_capacity.py` 里
  向量数远小于切片数）；
- **迁移后没重启 worker**：worker 还连着旧队列/旧库，任务写回旧位置；
- **反向迁移（pg → json）不支持**：降级路径只保证"能起来"，不保证"数据完整"，
  真要退回请用备份恢复。

### 5.2 多副本（水平扩容）

`run_registry` 原来只活在进程内存里，于是「用户刷新页面 → 负载均衡打到另一个
副本 → 那个副本没听过这次运行 → 404」。现在每次运行的非 delta 事件都写进
`run_events` 表，任何副本都能从第 0 条重放并跟到结束，`GET /api/agent/runs/active`
也会把「别的副本上还在跑的那一轮」一起列出来。`delta` 帧刻意不落库——重连时
正文会从会话历史里取回来，为一帧一个字写一行库不划算。

起第二个副本之前，先逐条确认这些**必须共享**的东西：

| 依赖 | 检查方式 | 不满足会怎样 |
|---|---|---|
| `APP_STORE_BACKEND` = `postgres` | `echo $APP_STORE_BACKEND` | 各副本各写一份本地文件，配置与会话彻底分叉 |
| `APP_VECTOR_BACKEND` = `milvus` | `python tools/check_infra.py --skip-llm` | `memory` 后端每副本一份向量，A 刚入库 B 检索不到 |
| `APP_QUEUE_BACKEND` = `redis` | `redis-cli -p 6380 ping` | `local` 队列靠 `jobs` 表抢，能跑但冲突面大 |
| 检查点不是 `memory` | `python -c "from app.services import checkpoints; print(checkpoints.resolve_mode())"` | 续跑落在另一副本时找不到检查点，确认后无法继续 |
| 限流计数走 Redis | 同上一条的 `redis-cli ping`（同一个实例） | 限流退化成每副本各算一份，实际配额被放大 N 倍 |

注意检查点这一行：`auto` 在 Linux + postgres 主库下会选 `postgres`（多副本共享），
但 **Windows 上一律退回 `sqlite`**（psycopg 不支持 Proactor 事件循环）——所以
多副本只能在 Linux 上跑，这不是配置能绕过去的。

都满足后，直接加副本即可——不需要粘性会话。仍有两处「每副本各一份」但不影响
正确性：BM25 倒排表缓存（按库签名自动重建，只是内存 ×N）、HTTP 连接池。

自检：开两个副本，在 A 上发起长任务，杀掉 A，再刷新页面——任务应该在 B 上
接着输出。若刷新后变成 404，看 worker 日志里有没有 `[run-events] 写入失败`，
以及 `run_registry.stats()` 的 `memory_only` 是否不为 0。

## 6. 容量与性能基线（本机实测）

| 场景 | 结果 |
|---|---|
| 1 万切片向量检索（memory / numpy） | 55 ms |
| Milvus HNSW 检索（23 条） | 与暴力余弦逐条一致，top1 score 0.994 |
| 检索接口端到端（含远程嵌入） | 约 1.0 s，瓶颈在嵌入端点 |
| 异步摄取一个 CSV | 4.6 s（解析 → 1 次嵌入 → 入库） |
| PostgreSQL 建表 + 查询 | 156 ms（首次） |

估算：`chunks` 表 100 万行时，检索走 Milvus、回表按主键取 3~4 条，延迟仍在几十毫秒；
真正的瓶颈会是嵌入吞吐，需要调大批量嵌入或换本地 GPU 端点。

### 6.1 出报告，而不是拍脑袋

容量不是一次性能测出来的，是跟着数据长出来的。每次变更（换嵌入模型、调切片大小、
扩库）之后跑一次，把输出存进变更记录，两次一对比就知道斜率：

```bash
cd server
python tools/report_capacity.py                     # 规模 + 磁盘占用
python tools/report_capacity.py --probe "死锁"      # 附带实测一次检索
python tools/report_capacity.py --json > cap.json   # 机器可读，便于画趋势
```

实测（2026-11-09，本机，1 个库 / 61 文档 / 5258 切片 / postgres 104 MB）：

| 指标 | 数值 | 说明 |
|---|---|---|
| 检索端到端（hybrid，top_k=4） | 3481 ms | **这是降级路径的数**：Milvus 集合维度与当前嵌入模型不一致，每次检索都在内存里暴力打散 |
| 同一路径（向量索引正常时） | 约 1.0 s | 瓶颈在远程嵌入请求，不在召回 |
| 磁盘 | 数据 104 MB / 上传 13 MB | 61 篇文档 50 MB 原始 + 5258 切片 |

**这张表最该看的是"向量数 0"**。规模里有 5258 个切片，向量却是 0，说明索引里
根本没有当前这批切片——检索正在降级。查法：

```bash
python tools/report_capacity.py            # 向量数与切片数差一个量级就是没写进去
docker exec einstein-milvus ...            # 或直接看服务日志里的"维度冲突"
```

修法是重建集合（会重新嵌入全部切片，按 4 万字符/批大约每千片 1~2 分钟）：

```bash
python tools/rebuild_vector_index.py --reembed --drop
```

### 6.2 容量规划的三个数

规划不需要模型，只需要三个实测值 + 一条除法：

1. **单切片平均字节**：`chunks 表大小 ÷ 切片数`。决定磁盘。
2. **单次检索的嵌入成本**：一次查询嵌一次（约 30 token），与库大小无关。
3. **每千片检索延迟**：决定"多大库必须上 Milvus"，而不是继续用 numpy 暴力。

按当前数据（5258 片 / 50 MB 原文 / 3481 ms 降级延迟）推算：

| 规模 | 切片 | 估磁盘 | 估检索（降级） | 建议 |
|---|---|---|---|---|
| 小团队 | < 1 万 | < 200 MB | 3~4 s | 可先不修索引，但要盯延迟 |
| 部门 | 10 万 | 约 2 GB | 30 s+（不可用） | **必须** Milvus + BM25 缓存 |
| 全公司 | 100 万 | 约 20 GB | — | Milvus 集群 + 独立嵌入服务 |

## 7. 故障手册

| 现象 | 常见原因 | 处理 |
|---|---|---|
| 所有接口 401 | 前端 `/api` 没反代到后端 / 令牌过期 | 查 nginx `proxy_pass`；重新登录 |
| 回答不流式 | nginx 缓冲未关 | `web/nginx.conf` 的 `proxy_buffering off` |
| 入库 503 | 嵌入端点不可用 | `check_infra.py --skip-llm`；看端点日志 |
| 任务一直 pending | worker 没起 / Redis 不可达 | `docker compose ps worker`；`queue.stats()` |
| worker 起来几秒就退出、退出码 0 | 旧版本 redis-py 版本差异导致槽线程死掉 | 已修；若仍出现，看日志里有没有 `领取任务失败`，确认 Redis 可达 |
| 任务一直 running 不动 | worker 崩了但租约未过期 | 租约 5 分钟自动回收；或 `POST /api/jobs/{id}/retry` |
| 刷新页面后任务消失、`/api/agent/runs/active` 是空的 | 运行事件没落库（库不可达，或 `run_events` 表没建） | 日志里找 `[run-events] 写入失败`；`run_registry.stats()` 的 `memory_only` 不为 0 即确认；跑一次 `migrate(get_db())` 建表（迁移 21） |
| Milvus 检索为空 | 集合是空建的 / 集合名换了 | `python tools/rebuild_vector_index.py --drop` |
| 维度冲突报错 | 换了嵌入模型但沿用旧集合 | 换 `APP_MILVUS_COLLECTION` 名或重建时加 `--drop` |
| 上传超过 50MB 被拒 | 服务端上限 | 拆分文件；需要更大改 `parsers.MAX_BYTES` 与 nginx `client_max_body_size` |
| 传图片报「需要 OCR 才能读这张图」 | 没配 `APP_OCR_MODEL`，也没装 pytesseract | 二选一：设 `APP_OCR_MODEL` 指向支持图片的 OpenAI 兼容模型，或 `pip install pytesseract` 并装 `chi_sim` 语言包 |
| 扫描件 PDF 报「需要把页面渲染成图再 OCR」 | 缺 pymupdf，pypdf 只能抽文本层 | `pip install pymupdf` 后重启 backend/worker；不想装就把 PDF 转成可复制文本再传 |
| 图片 OCR 太慢 / 报超时 | 一次识别一页，长图或高分辨率原图很吃时间 | 调小 `APP_OCR_MAX_SIDE`（默认 2000）省 token；扫描件走 `/documents/async` 而不是同步上传 |
| 扫描件只进来前几页 | `APP_OCR_MAX_PAGES` 默认 20 | 属预期（防 200 页跑一下午），正文末尾会写「共 N 页，只识别了前 M 页」；调大该值后**重新上传同一文件**（原文件摄取后已删，`reindex` 只重切已有正文，不会重新 OCR） |
| 目录导入返回 403 | 未配置允许根（默认关闭） | 在 `.env` 配 `APP_LOCAL_IMPORT_ROOTS=绝对路径,逗号分隔` 后重启 backend |
| 批量导入整批卡住 | 单批文件太多、嵌入排队 | 看 `GET /api/jobs/{id}` 的 `done/total`；一个目录会按 `APP_IMPORT_BATCH_SHARD`（默认 50）拆成多片，逐片看哪个还在排队 |
| 批量导入很慢、CPU 却很闲 | worker 只有 1 个槽，多片在排队 | 加大 `--concurrency`（受嵌入端点上限约束，本地单卡 2~4 够用） |
| 导入后磁盘没降 | 分片任务抢占同一批次目录，文件被占用删不掉 | 已加 `stale_files` 计数与启动兜底清理（`APP_IMPORT_STAGING_TTL_HOURS`，默认 6 小时）；急着释放可停服务后清 `data/uploads/batch-*` |
| 大量任务 failed 且都指向同一个已删库 | 删库时任务还在队列里 | 属预期（handler 直接判永久失败，不重试）；队列记录可按需清理 |
| 智能体写文件被拒「不在任何项目内」 | 引擎强制先有项目，产物预览/下载按「项目+相对路径」拼 | 让模型先 `project_create`，再写 `/项目名/文件`；提示词里已写明 |
| 智能体跑完了但没看到计划块 | 简单任务（一两步）模型按提示跳过 write_todos | 属预期；复杂多步任务才会出计划 |
| 想回退到旧的单循环智能体 | 引擎切换 | `.env` 设 `APP_AGENT_ENGINE=react` 重启；事件协议一致，前端无感 |
| 磁盘涨得快 | 上传原文件与 audit 累积 | `data/uploads` 正常应被消费删除；audit 有 `MAX_ENTRIES` 上限 |
