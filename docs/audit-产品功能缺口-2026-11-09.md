# 产品功能缺口全量盘点

- 盘点日期：2026-11-09
- 盘点对象：Einstein v0.6.1（`server/app` + `web/src`）
- 视角：产品（用户旅程与闭环），不含技术债与架构决策——那部分是架构师的产出
- 方法：读代码确认「有没有」与「断在哪一环」，基线事实由主理人提供，本文只做增量核对与影响面判断

---

## 一、一句话结论

**产品现在是「API 完整、界面半成品」**：后端已有 95 个接口，但其中**整套知识库管理能力在前端没有任何入口**——切片查看、切片编辑、删除单篇文档、单篇重建、版本列表、版本回滚，六个后端接口前端一次都没调用（`web/src` 全域搜索零命中）。用户能上传，却管不了自己传的东西。

最短板有三条，按影响面排序：

1. **界面没跟上后端**（P0，成本最低收益最高）：不是缺功能，是缺「让功能被看见」的那层界面；
2. **没有共享模型**（P0）：知识库/专家/技能按创建者隔离，第二个人登录就看不到同事的劳动成果；
3. **没有可信度证明与成本账本**（P0）：回答不了「它准不准」和「花了多少钱」这两个采购必问题。

当前版本适合单人试用与 demo，离可交付还差**一个管理界面、一个共享模型、一本账**。

## 三、「有入口但不成闭环」清单

功能做了 70%，用户走到一半断掉——这是本产品最典型的形态，也是投入产出比最高的修复区。

> **先单列最严重的一条**：知识库「文档管理」的断点不在 70%，而在 **30%**。后端六个接口全都写完并有测试，前端**一个都没接**：`web/src` 全域搜索 `chunks / versions / rollback / reindex` 只命中技能页（`SkillsPage.tsx`），KB 域零命中。结果是一份传错的合同、一片切坏的表格、一次失败的摄取，用户在界面上**没有任何补救手段**，唯一路径是删掉整个知识库重传。这不是「缺功能」，是「后端能力对用户完全不可见」，也是本报告投入产出比最高的一项。

| # | 功能 | 现状证据 | 断在哪一环 | 修复成本 |
|---|---|---|---|---|
| 0 | 知识库文档管理（切片/版本/删除/重建） | 6 个后端接口齐全（`kb.py:469/493/512/528/543/563`），`KbPage.tsx:318-333` 只显示名称与切片数，全前端零调用 | **断在界面**：不是不会做，是没做 | **低（纯前端，接口与测试都现成）** |

> 2. 技能 **zip 导入/导出已实现**（`routes/skills.py:221-256`，50MB 上限），**试运行也有**（`:261`，但只是提示词回放，不跑工具）。

> 4. 上述四项都**不该算「缺失」**，应归入「已有但不成闭环」——它们缺的不是能力，是运营闭环与界面暴露。

| 3 | 团队空间（知识库、应用与成员的归属与共享） | Dify 工作空间、FastGPT 团队版 | 是，多人第一诉求 | **P0，v0.7.0 必做** |
| 4 | 发布与嵌入（免登录分享链接、iframe/JS 嵌入现有系统） | Dify、FastGPT、Coze | 是，「让业务同事直接用」的唯一路径 | **P1，v1.0.0** |
| 5 | 文档解析增强（OCR、复杂表格/图文混排还原） | RAGFlow 强项 | 是，但取决于客户类型 | **P1，v1.0.0** |
| 6 | 检索调优面板（chunk 可视化、召回调试、命中率曲线） | RAGFlow | 是，但只有 1-2 个管理员用 | P1，我们已有 60%（`search_compare` + chunks 编辑），补齐即可 |
| 7 | 日志与标注回流（LLM 日志 → 标注 → 数据集） | Dify | 是，是「越用越准」的机制 | **P0，v0.7.0**（我们只差把差评接进评测集） |
| 8 | 连接器同步（飞书/Notion/Confluence/网页站点） | Dify、RAGFlow | 分客户，中大型必备 | P1/P2，v0.8.0 起 |

**明确排除、我们不需要的**：

| 项 | 谁家在做 | 为什么我们不做 |
|---|---|---|
| 可视化工作流画布（拖节点连线） | Dify、Coze 的核心卖点 | 与我们「智能体自主规划（write_todos + task）」的定位正面冲突。上画布等于换产品，且要长期双轨维护。用「任务模板 + 计划确认」替代，成本约 1/10，覆盖 80% 场景 |
| 多租户 SaaS 计费/支付/订阅 | Dify Cloud、Coze | 我们是自托管定位，客户自己结算；做计费要背上账单、发票、退款，与核心价值无关 |
| 文生图/视频等多模态生成 | Coze、Dify 部分 | 知识库场景的核心是「让文档可被问答」，生成能力是另一个产品 |
| 通用插件市场生态 | Coze | 已有 GitHub 技能市场 + MCP 双通道，覆盖度足够；做市场运营是另一个团队的事 |

## 五、建议的三个版本切分

### v0.7.0 —— 可信度与闭环（先把已有能力的断点接上）

| # | 必做项 | 一句话验收标准 |
|---|---|---|
| 1 | **知识库管理闭环**：文档管理界面（切片查看/编辑、删除单篇、单篇重建、版本列表与回滚、失败重试） | 用户在界面上能定位到某一片切错的表格、就地改掉并只重建这一篇；传错的文件能单独删除而不影响库 |
| 2 | **共享模型**：库/专家/技能的可见范围（私有 / 工作区）+ 修正 `list_kbs` 按 owner 过滤 + UI 开关 | 新成员登录后在列表里能看到同事共享的库与专家，直接提问且答案带引用；切换为「私有」后对方 404 |
| 3 | **检索质量闭环**：重排默认打开 + 一组开/关基线数据 + 负例集 + 差评一键进评测集 + 评测 A/B 并排 | 同一评测集一次跑出「重排开/关」两列对比；负例题的「未命中率」可读；差评能一键变成用例 |
| 4 | **可信对话**：重新生成 + 编辑后重发 + 赞踩采集原因 | 不改问题就能重答一次，两版答案都在历史里可对比；差评能填一句原因 |
| 5 | **运行可见可控**：按 run 的轻量 trace（工具名/耗时/成败/检索耗时/token 归属到 user+ws）+ **前端接上 `GET /agent/runs/{id}/stream` 重连** + 审批默认开（`agent_approval_tools=code_run`）+ 管理页开关 | 刷新页面后正在跑的任务能自动重新订阅、继续显示进度；打开一次失败的运行能看到第几步、哪个工具、花了多少 token；默认部署下写文件/跑命令前一定弹确认 |

### v0.8.0 —— 团队与运营（让管理员能管、能算账）

| # | 必做项 | 一句话验收标准 |
|---|---|---|
| 1 | 模型注册表 + 按专家/会话选模型 + 连通性检查 | 管理员加一个端点 → 一键测试 → 指定给某个专家 → 该专家对话真的走新模型 |
| 2 | 成本看板（模型 × 成员 × 工作区 × 天，单价可配） | 能回答「上月谁花了多少钱、哪个专家最贵」，金额与实际账单误差 < 5% |
| 3 | 告警（配额触顶/错误率/模型不可用/未命中率）+ 通知渠道 | 模型挂掉 5 分钟内收到通知；配额到 80% 提前预警 |
| 4 | 文档源同步（URL 重新抓取 + 定时检查 + 变更提示） | 源页面改版后，系统提示「3 篇文档疑似过期」，用户一键更新并保留旧版本 |
| 5 | 知识库级权限 + 成员用量视图 | 能把某库限定给指定成员/角色，越权访问返回 404 且进审计 |

### v1.0.0 —— 可交付（能卖、能救、能嵌）

| # | 必做项 | 一句话验收标准 |
|---|---|---|
| 1 | OCR（图片 + 扫描 PDF）+ 图片格式摄取 | 一份扫描版合同上传后可检索、可引用原页 |
| 2 | 备份运营化（定时 + 保留策略 + 恢复演练脚本 + 恢复后自检） | 演练文档可被第三方照着执行，从备份到服务可用 < 30 分钟 |
| 3 | 发布与嵌入（免登录分享链接 / iframe） | 非技术同事拿到一个链接就能用，无需注册 |
| 4 | 会话导出（md/json）+ 引用可带走 | 导出的 md 里引用编号能定位回原文档 |
| 5 | 容量基线与升级手册（含迁移路径 json→sqlite→postgres） | 运维手册覆盖「从 10 万片扩到 100 万片」的具体步骤与阈值 |

## 六、不建议做的事

| # | 项 | 看起来诱人的理由 | 为什么现在不该做 |
|---|---|---|---|
| 1 | 可视化工作流编排画布 | Coze/Dify 都有，客户会问「你们能拖拽吗」 | 与「智能体自主规划」的定位冲突：一旦有画布，产品叙事要重写，且两条执行路径要长期分别维护。真需求用「任务模板（预置提示词 + 工具白名单 + 输出格式）+ 计划确认」满足，20% 成本覆盖 80% 场景。等 v1.0 之后再看是否有真实付费信号 |
| 2 | 自研推理调度/多模型路由网关（vLLM 集成、GPU 池化、模型热切换） | 「一站式」听着很美 | 自托管客户自带推理端点，我们只需 OpenAI 兼容。做调度等于变成基础设施产品，与「知识库 + 智能体平台」定位偏离，且要背 GPU 运维的坑 |
| 3 | 文档级 ACL（每个切片/每篇文档单独授权） | 「更细粒度更安全」 | 检索侧要带权限过滤，会让召回、缓存、评测全部复杂化；而用户实际诉求是「这个库给谁看」。**先做知识库级可见范围，把 5.1/5.2 修好，文档级 ACL 等有明确合规客户再谈** |
| 4 | 会话/答案的社交化（点赞排行、热门问答、评论区） | 提升活跃度 | 企业知识库是「查完就走」的工具型产品，社交化收益低、审核成本高；先把答案准确率与引用可信度做好，比做社区重要一个数量级 |
