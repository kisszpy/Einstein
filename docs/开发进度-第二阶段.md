## 1. 环境能力确认（2026-11-07 实测）

| 项 | 结论 | 证据 |
|---|---|---|
| Docker CLI | ✅ 29.6.1 | `docker --version` |
| Docker 守护进程 | ❌ **起不来** | backend 崩溃：`rename ~/.docker/daemon.json.tmp → daemon.json: Access is denied` |
| WSL | ⛔ 被系统安全策略禁用 | `wsl.exe` 在黑名单，无法执行 |
| 主机资源 | ✅ 充足 | 125.7 GB 内存 / 88.5 GB 可用；C 盘 231 GB 可用 |
| 本地 PG/Redis/Milvus | ❌ 均未安装 | `psql`/`redis-cli` 不存在；5432/6379/19530 无监听 |
| Python 依赖 | ⚠️ 缺关键包 | 有 numpy? 无；psycopg/pymilvus/redis/sqlalchemy 全无；bs4/httpx 有 |

**判断**：容器化路径在资源上完全可行（Milvus standalone 三容器约 3 GB），唯一阻塞是 Docker Desktop 守护进程需要在沙箱外由人工启动一次。启动后本机可真实跑 Postgres 16 + Redis 7 + Milvus 2.4。

**因此 S2.0 的第一动作是环境自检，且必须做到"两条腿走路"**：抽象层先行，容器可用则接线真实后端，不可用则退回本地实现——任何一步都不因为 Docker 而停工。

## 5. 技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| ORM | 不用 SQLAlchemy ORM，用原生 SQL + `psycopg` / `sqlite3` | 现有模型是 dataclass，上 ORM 要重写全部模型；原生 SQL 迁移成本低、可控 |
| 向量库 | Milvus 为主，`MemoryIndex`(numpy) 兜底 | Milvus Lite 不支持 Windows，只能容器；但必须保留无容器可跑路径 |
| 队列 | `LocalQueue`（DB + asyncio）默认，Redis 可选 | 单机也需异步摄取；Redis 主要在横向扩展时需要 |
| 限流 | 自写令牌桶（Redis Lua / 内存） | 不引额外依赖，规则自定义更灵活 |
| 迁移 | 自写轻量 runner + `schema_version` 表 | 项目规模不值得引 Alembic |
| 鉴权 | 现有 JWT + `tenant_id` / 角色声明 | 不重做认证体系 |
| 查询改写 | 小 prompt + 缓存，失败回退原 query | 本地 27B 生成慢，改写必须严格限 token 且有兜底 |

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Docker Desktop 起不来（当前已发生） | 无法验证 PG/Milvus/Redis 真实链路 | 抽象层 + SQLite/numpy 兜底；Docker 就绪后再补跑一次生产后端验证 |
| 抽象层改造波及 12 个 service | 回归面大、可能引入隐性 bug | 保留 JSON 实现做对照；每模块切换后跑全量巡检；三个后端跑同一套用例 |
| 本地 27B 加查询改写后首字延迟上升 | 体验变差 | 改写限 64 token、命中缓存、超时 1.5 s 直接走原 query |
| Reranker 模型文件缺失 | 重排不可用 | 三级降级：本地端点 → onnx → 关闭，配置驱动 |
| Milvus standalone 在 Windows 容器的 volume/网络问题 | S2.1 阻塞 | 先用 `milvusdb/milvus:v2.4.x` 官方 compose；失败则先用 Postgres `pgvector` 替代（同为容器，更轻） |
| 长任务中断恢复依赖 checkpointer 表结构 | 改造成本 | 与 S2.1 的 Repository 同期设计，避免二次迁移 |
